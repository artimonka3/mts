# План разработки Backend МТС: трек №2

Дата: 14 октября 2026 года. Статус: предложение на утверждение. Backend-код в рамках этого плана не создаётся.

## 1. Основание и главная идея

План учитывает ТЗ конкурса, вводную команды, схемы из `/Users/artemgolak/Documents/FAMCS/mts/` и добавленную `govorLLM_backend/LLM.canvas`. Файлы архитектуры описывают желаемое поведение; проверенного backend-кода в переданной папке пока нет. В схеме БД уже указан PostgreSQL. Отдельные файлы «Архитектура БД.canvas» и «Поиск договорённости.canvas» пока содержат пустые объекты.

Добавленная схема уточняет последовательность: результат анализа → предложение с прямой цитатой → проверка пользователем → принятая задача → календарь/CRM. Summary звонка и накопленное описание клиента — отдельные результаты. Названия пустых заметок о хорошем качестве модели, промпте и QLoRA считаем вариантами будущих экспериментов. Проверенные модель, точность и требования к железу пока не определены.

**Сначала строим backend, который умеет принимать, хранить, проверять и использовать результаты анализа. Подключение настоящей LLM — самостоятельный последующий этап.**

Основной путь MVP:

```text
Загрузка аудио / файл браузерной записи / известный демо-звонок
    → защищённое хранение + задание обработки
    → проверка и подготовка аудио
    → версия расшифровки с репликами и говорящими
    → заглушка анализа для известного демо / ручной ввод
    → кандидаты договорённостей + цитаты + summary
    → принять / исправить / отклонить
    → задачи + напоминания + календарное представление
    → .ics + Excel + локальная имитация CRM
    → дашборд
```

Для произвольной записи заглушка не придумывает договорённости. При доступном ASR показываем настоящую расшифровку и ручное создание задач; при недоступном ASR сохраняем файл и показываем соответствующее состояние. Полный автоматический сценарий до подключения моделей существует только для заранее подготовленного демо.

Требование ≥90% в PDF относится к распознаванию ключевых фраз при транскрибации. Качество извлечения всех полей договорённости измеряется отдельно. Загрузка после звонка и экспорт .ics не означают полного выполнения требований обработки во время звонка и автоматической внешней синхронизации.

## 3. Предлагаемая техническая основа

Один модульный backend и отдельный процесс worker, общая PostgreSQL. Модули разделяем по функциям внутри одного проекта. Это позволяет развивать систему без распределённых транзакций между сервисами.

| Компонент | Предложение | Зачем |
|---|---|---|
| HTTP API | FastAPI + Pydantic | API для React и проверка входящих/исходящих структур |
| База | PostgreSQL | Уже предусмотрена архитектурой; данные, задания и события доставки |
| Доступ к БД | SQLAlchemy + Alembic | Модели, транзакции и последовательные миграции |
| Обработка аудио | FFmpeg/ffprobe | Проверка файла, метаданные и подготовка входа для ASR |
| Фоновые задания | Отдельный worker, таблица jobs | Обработка переживает перезапуск API, есть повторы и понятные ошибки |
| Хранение файлов | Интерфейс AudioStorage, локальная реализация для MVP | Позже можно сменить хранилище без изменения предметной логики |
| Распознавание | ASRProvider и DiarizationProvider | Настоящие адаптеры после проверки железа, fixtures для разработки |
| Текстовый анализ | AnalysisProvider с заглушкой | Backend не зависит от выбора LLM и её протокола |
| Локальный запуск | Docker Compose: API, worker, PostgreSQL, mock CRM | Воспроизводимый стенд для команды |
| Проверки | pytest, интеграционные проверки с PostgreSQL | Проверка переходов, сохранности правок, повторов и доступа |

Redis/Celery сейчас не обязательны. Для небольшой нагрузки worker забирает jobs из PostgreSQL. Это наше архитектурное решение: PostgreSQL поддерживает захват строк с `SKIP LOCKED`, в том числе для таблиц, работающих как очередь. [Документация PostgreSQL](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)

Длительные FFmpeg/ASR/analysis не выполняем внутри HTTP-запроса и не делаем их надёжность зависимой от `BackgroundTasks` API-процесса. FastAPI рекомендует отдельные процессы для тяжёлых фоновых вычислений. [Документация FastAPI](https://fastapi.tiangolo.com/tutorial/background-tasks/#caveat)

SQLAlchemy Session принадлежит одному запросу или одной задаче. Транзакция не должна оставаться открытой во время распознавания или вычислений. [Документация SQLAlchemy](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#is-the-session-thread-safe-is-asyncsession-safe-to-share-in-concurrent-tasks)

## 4. Решения о данных, которые принимаем до реализации

### Сущности

| Сущность | Основное содержание |
|---|---|
| Organization, User, Session | Принадлежность данных, вход, завершение сессии |
| Client | Карточка клиента, история связанных звонков; это не обязательно пользователь приложения |
| Call | Владелец, клиент, дата разговора, timezone, язык, источник, признаки демо, состояние обработки |
| CallParticipant | Участник разговора, отображаемое имя, роль; возможная связь с User или Client |
| AudioAsset | Оригинал и производные файлы, формат, длительность, размер, ключ хранения, срок удаления |
| ProcessingJob | Стадия, попытки, ошибка, время следующей попытки, lease и прогресс |
| TranscriptRevision, Segment | Версия текста, реплики, анонимный speaker, таймкоды; оригинальная расшифровка сохраняется |
| AnalysisRun | Какая версия текста и настроек использована, источник результата: mock/manual/будущая модель |
| CallSummary | Резюме беседы и черновик текста для клиента, версия и происхождение |
| Agreement | Действие, обязанный участник, адресат, срок, приоритет, проверка и выполнение |
| AgreementEvidence | Источники: версия расшифровки, сегменты, цитата, контекст, диапазон текста и при наличии время |
| Tag, TaskTemplate, TriggerRule | Классификация и настройки пользователя; версии правил |
| Reminder, Notification | Когда напомнить, кому показать внутри приложения, факт доставки/прочтения |
| OutboxEvent, DeliveryAttempt | Надёжная отправка изменений в mock CRM и будущие адаптеры |
| AuditEvent | Доступ к записи и тексту, правки, подтверждения и удаление без копирования чувствительного текста в лог |

ClientFact и ClientProfileSummary вводим отдельной миграцией во второй очереди. Для подтверждённого факта нужен источник и возможность исправления; автоматическую «биографию» без проверенной LLM пока не строим.

**Задача в MVP — представление принятой Agreement.** Не создаём вторую копию всех полей в Task: иначе срок, статус и описание начнут расходиться. Когда появятся самостоятельные задачи без договорённостей или несколько задач на одно обязательство, пересмотрим это решение отдельной миграцией.

### Независимые состояния

- Обработка: файл получен → очередь → подготовка → расшифровка → текст доступен; ошибки и отмена отдельно. Состояние анализа хранится отдельно: не подключён / ожидает / выполняется / готов / ошибка.
- Проверка договорённости: предложена → принята либо отклонена. Ручная правка принятой задачи владельцем сохраняется через «Сохранить и подтвердить» как подтверждённая новая версия. Автоматический повтор анализа сам подтверждение не снимает. Если пользователь явно снимает подтверждение или отклоняет ранее принятую карточку, активные напоминания прекращаются, ожидающие события доставки отменяются и в mock CRM передаётся событие отзыва.
- Выполнение: открыта → в работе → выполнена либо отменена. Модель может предложить смысловую классификацию, но не управляет фактическими переходами задачи самостоятельно.
- Просрочка вычисляется из срока, текущего времени и незавершённого состояния. Это не самостоятельный сохранённый workflow-статус.

У «speaker_1» нет автоматически известного имени. Говорящий, контакт и аккаунт — разные сущности. Пользователь может сопоставить speaker с участником. Стерео также не гарантирует, что в каждом канале записан отдельный человек.

### Сроки, уверенность и источники

- У звонка отдельно сохраняются время разговора и время загрузки. Для относительных дат используется время разговора в его timezone, по умолчанию Europe/Minsk.
- Срок бывает date-only, точное время, интервал либо неизвестен. Сохраняем исходную фразу и признак неоднозначности.
- «Через 3 дня» считается от даты разговора. Для «до пятницы», если разговор был в пятницу, нужна явная политика или подтверждение; неоднозначность не превращаем молча в точный срок. Отсутствующие год и время также не выдумываем.
- Неизвестные участники и срок допустимы как null с причиной. Требующие уточнения задачи видны пользователю, но без нужных данных не отправляются во внешние интеграции.
- Confidence хранится с происхождением и может отсутствовать. Если пользователь меняет оценку уверенности, сохраняем override отдельно от исходной оценки. Число из mock не является вероятностью или метрикой качества.
- Evidence ссылается на конкретную неизменяемую версию текста. Диапазоны текста описываем однозначно, включая единицу отсчёта символов. Для диалога «просьба → согласие» у одной договорённости может быть несколько источников.
- Правка расшифровки создаёт новую версию. Старое доказательство остаётся доступным до истечения его срока хранения; относительно новой версии отмечаем необходимость перепроверки. Неизменяемость версии защищает её от перезаписи, но не препятствует удалению по политике хранения.
- Повторный анализ создаёт новый run и предложения. Принятые карточки и пользовательские изменения он не перезаписывает.

## 5. Порядок разработки

### Этап 1. Мини-ТЗ, договорённости о поведении и контракты

**Что делаем:** описываем четыре экрана через backend-сценарии; фиксируем поля, состояния, переходы, ошибки, политику подтверждения и сроки. Определяем единый формат ошибок, пагинацию, фильтры и набор API. Разделяем реальные и демонстрационные данные.

Параллельно начинаем эталонный набор 20–30 диалогов: разметка реплик, ключевых фраз, обязательств, участников, сроков и evidence. Добавляем отрицательные примеры, отмену, перенос срока, условные обещания и неоднозначные даты. Демо-данные и закрытый набор оценки должны быть отделены по звонкам.

**Получаем:** mini-ТЗ, первичную ERD, API-контракты и правила приёмки. Здесь утверждаем предметную логику до создания таблиц.

**Готово, когда:** один пример разговора можно вручную провести от загрузки до календаря; для каждого поля известны смысл, допустимые значения и источник.

### Этап 2. Каркас приложения и воспроизводимый запуск

**Что делаем:** создаём backend-проект, конфигурацию, lock зависимостей, FastAPI, health/readiness, PostgreSQL, Alembic и базовый worker-процесс. Добавляем Compose, `.env.example`, команды миграций и запуска. Сразу ограничиваем CORS и исключаем чувствительные данные из логов.

Предлагаемые модули: `auth`, `clients`, `calls`, `audio`, `processing`, `transcripts`, `analysis`, `agreements`, `tasks`, `reminders`, `integrations`, `dashboard`, `audit`. Внутри нужны понятные API-обработчики, сервисы бизнес-логики и слой хранения; отдельный сервис на каждый модуль не нужен.

**Получаем:** пустой, но запускаемый стенд без моделей и GPU.

**Готово, когда:** новый разработчик запускает сервисы по инструкции; API и worker видят БД, миграции применяются с нуля.

### Этап 3. БД, вход и принадлежность данных

**Что делаем:** создаём базовые миграции User/Organization/Client/Call и таблиц результатов, внешние ключи, ограничения и индексы. Последующие функциональные таблицы добавляем по этапам. Организация заложена для развития, но в MVP доступ ограничен владельцем: принадлежность одной организации сама по себе не даёт доступ к чужим звонкам.

Для MVP предлагаем вход по паролю и серверную сессию; тестовые пользователи создаются seed-командой. Нужны logout, срок сессии, безопасное хранение паролей, ограничение попыток входа и защита cookie/изменяющих запросов при веб-развёртывании. Регистрация, восстановление пароля и корпоративный SSO — следующая очередь.

**Получаем:** пользователь работает только со своими клиентами, звонками и задачами. Проверка доступа действует также на файлы, источники и экспорт.

**Готово, когда:** два тестовых пользователя не получают данные друг друга, даже подставляя известный ID в URL.

### Этап 4. Клиенты, звонки и приём аудио

**Что делаем:** CRUD клиентов и метаданных звонка; загрузку файла; отдельное создание известного демо-звонка. Браузерная запись поступает как обычный файл; включение микрофона и отображение предупреждения делает frontend.

API принимает аудио порциями, проверяет лимит размера и хранит по уникальному ключу, связанному с call_id. Проверяются реальные метаданные, а не только расширение. Начальные конфигурируемые ориентиры для стенда — до 100 МБ и до 60 минут; окончательно сверяем с тестовыми файлами. Длительность проверяется после загрузки. Обязательны лимиты запроса, диска и времени работы декодера. [FastAPI UploadFile](https://fastapi.tiangolo.com/tutorial/request-files/)

Сохраняем дату разговора, timezone, источник `upload/browser_recording/demo`, подтверждение показанного уведомления и сведения о разрешении на обработку. Backend фиксирует свидетельство, доступное приложению, а не объявляет согласие второй стороны доказанным только по checkbox. Для ранее записанного файла пользователь подтверждает право загрузки и обработки.

**Получаем:** Call + AudioAsset + job, HTTP `202 Accepted`, идентификатор и URL состояния. Файл доступен через проверяемый endpoint, без публичного статического URL.

**Готово, когда:** запись из браузера и обычная загрузка проходят одинаковый путь; повреждённый/слишком большой файл даёт понятную ошибку; повтор запроса с тем же idempotency key не создаёт копию звонка.

### Этап 5. Надёжный worker и подготовка аудио

**Что делаем:** реализуем jobs: короткий захват задания, lease/heartbeat, ограниченные повторы с задержкой, ошибки по стадиям, отмену и восстановление после перезапуска. Повторы технического задания не создают второй комплект результатов.

Предобработка: ffprobe → сохранение исходных каналов → конвертация под требования выбранного ASR → определение наличия речи. WAV 16 kHz mono PCM16 подходит как первоначальный профиль, но параметры принадлежат адаптеру ASR. Нормализацию и шумоподавление включаем после сравнения с исходным звуком; они могут ухудшать распознавание. VAD можно добавить отдельным адаптером.

В исходной схеме предлагается обрезать длинные тишины. Для первой версии **сохраняем исходную временную шкалу**, чтобы таймкоды совпадали с оригиналом. При обработке отдельных интервалов учитываем их исходные смещения. Фиксированные имена `clean.wav`/`call_stereo.wav` заменяем ключами конкретного звонка.

**Получаем:** отдельный процесс выполняет подготовку, API показывает текущую стадию, результаты сохраняются атомарно. Удалённый звонок не может воскреснуть из запоздалого job.

**Готово, когда:** остановка worker и повтор запуска восстанавливают работу; повтор задачи не создаёт дубликаты; тишина, повреждение и timeout имеют разные понятные причины.

### Этап 6. Расшифровка, говорящие и редактирование

**Что делаем:** TranscriptRevision и Segment, порядок реплик, язык, speaker_id, времена начала/конца; импорт fixtures и ручную правку с созданием новой версии. Сопоставляем говорящих с участниками отдельно.

Сначала fixture ASR для известного демо и импорт эталонного текста. Настоящий ASR подключается отдельным адаптером, когда он проверен на доступном железе; это не требует выбора LLM. Если ASR ещё не готов, остальные этапы развиваются на известных расшифровках.

Whisper-транскрибация и diarization — разные задачи. Таймкоды сегментов не дают идентичность говорящего. В API разделение по говорящим показываем лишь там, где оно реально доступно или задано в демо; иначе обозначаем unknown. [Whisper](https://github.com/openai/whisper/blob/main/whisper/transcribe.py), [pyannote.audio](https://github.com/pyannote/pyannote-audio)

**Получаем:** backend для экрана расшифровки с репликами и аудио-переходом к источнику.

**Готово, когда:** текст редактируется без потери первоначальной версии; таймкоды относятся к оригинальному файлу; отсутствующее разделение говорящих обозначено явно.

### Этап 7. Заглушка анализа, summary и обработка результатов

**Что делаем:** вводим внутренний контракт AnalysisProvider. На вход: версия реплик, участники, дата звонка/timezone, версия правил и при необходимости подтверждённый клиентский контекст. На выходе для приложения: предложения договорённостей с evidence, summary звонка и черновик summary для клиента. Будущий адаптер преобразует фактический ответ модели в этот внутренний формат.

Контракт приложения не фиксирует модельный HTTP API, промпт, формат serving, число вызовов, размер контекста или обучение. В этой версии есть только `DemoAnalysisProvider` и состояние «анализ не подключён». Демо-провайдер работает по известному сценарию и согласованной версии расшифровки; после изменения текста не выдаёт старые цитаты как актуальные.

Summary можно исправить вручную. Отправка клиенту сейчас не выполняется: backend хранит текст для копирования. Автоматическое накопление фактов и связывание summary клиента остаётся следующей очередью; вводим для него отдельную границу модуля.

**Получаем:** весь backend развивается независимо от модельных тестов. Ответы маркированы `mock/manual`, недоступные значения остаются null.

**Готово, когда:** демо выдаёт проверенные карточки и ссылки на существующие реплики; произвольный звонок показывает отсутствие анализа и позволяет ручную работу.

### Этап 8. Договорённости, источники и подтверждение

**Что делаем:** список кандидатов звонка; создание вручную; редактирование любого отображаемого поля с сохранением исходного результата и override; принять/отклонить; причины ошибки; историю изменений и оптимистическую блокировку версии.

Источники хранят прямую цитату, левый и правый контекст, структурные ссылки на текст и таймкоды. Ссылки проверяем перед сохранением. Для ручной задачи можно выбрать источники или явно отметить, что источник не задан.

Кнопку «ошибка перевода» из схемы предметно уточняем: ошибка расшифровки, ошибка извлечения либо ошибка межъязыкового перевода, если перевод действительно появится. В API сохраняем точную причину. Принятие и выполнение остаются независимыми действиями.

**Получаем:** основной экран результата: предположение → цитата → корректировка → подтверждение. Summary виден независимо от того, приняли ли все кандидаты.

**Готово, когда:** неверный срок исправляется и подтверждается; отклонённый кандидат не становится задачей; повтор анализа и параллельная правка не уничтожают изменения пользователя.

### Этап 9. Задачи, сроки, теги и настройки

**Что делаем:** представление принятых договорённостей, фильтры по клиенту/сроку/статусу/приоритету/тегам, поиск в ограниченном наборе разрешённых полей, сортировку и пагинацию. Добавляем переходы выполнения и календарный диапазон.

Выносим правила даты в отдельную логику. Она проверяет и нормализует уже полученное выражение срока; полноценное понимание произвольной речи без LLM здесь не обещаем. Date-only становится просроченным после окончания указанного дня в timezone звонка/задачи, а не в начале этого дня.

Добавляем CRUD шаблонов задач и триггеров: фразы/примеры, активность, приоритет, теги, настройки напоминаний. Каждый analysis run получает снимок конфигурации. Без LLM триггеры являются сохранённой конфигурацией и тестовым preview, а не доказанной семантической системой извлечения.

**Получаем:** backend для экрана задач, календарного представления и настроек.

**Готово, когда:** карточка задачи и результат звонка показывают одни и те же данные; перенос/выполнение/отмена корректны; задачи без срока видны в отдельной группе.

### Этап 10. Календарный экспорт, Excel и mock CRM

**Что делаем:** `.ics` и `.xlsx` для одной задачи или разрешённой выборки. Экспорт учитывает фильтры и владельца. Excel содержит клиент, действие, участников, срок, приоритет, статус, теги, ссылку на звонок и источник; пользовательский текст не становится исполняемой формулой.

Для .ics предлагаем события `VEVENT`: встреча отображается событием; дедлайн — явно подписанной календарной отметкой «Срок: …». Дата без времени экспортируется как дата, без выдуманного часа. Храним стабильный UID и версию; проверяем Unicode и экранирование. Задачи без срока перечисляются в отчёте о пропусках экспорта. `.ics` — файл обмена, не двусторонняя синхронизация. [RFC 5545](https://www.rfc-editor.org/info/rfc5545/)

После принятия/изменения/выполнения/отмены создаётся outbox event в одной транзакции с изменением задачи. Worker отправляет его только в преднастроенный локальный mock CRM. Payload имеет event_id, agreement_id, версию и тип события. Приёмник умеет дедупликацию и upsert, а отправитель — повторы и обработку устаревших версий. Снятие подтверждения отзывает запись, а полное удаление создаёт tombstone только с идентификатором и версией, без удалённого текста; приёмник очищает данные и больше не принимает старые обновления. Уже скачанный .ics автоматически не отзывается: это граница файлового экспорта.

**Получаем:** демонстрируемый экспорт и автоматическая доставка в имитацию CRM. Интерфейс реального CRM/календаря можно позже реализовать без переделки Agreement.

**Готово, когда:** файлы открываются в календаре и Excel; повтор webhook не создаёт копию; недоступный mock CRM не теряет событие.

### Этап 11. Напоминания и уведомления внутри приложения

**Что делаем:** расписание напоминаний, worker-проверку времени, список уведомлений и отметку прочтения. Для deadline-only используем явно настроенное локальное время напоминания; unknown/неоднозначный срок требует уточнения. Подтверждение найденных деталей также появляется во внутренней очереди уведомлений.

Перенос срока отменяет устаревшие напоминания и создаёт новые. Выполнение/отмена/удаление задачи и снятие подтверждения выключают будущие напоминания. Повтор доставки не создаёт дубликат. Уведомление хранится, даже если браузер в момент срабатывания закрыт; пользователь увидит его при следующем входе.

**Получаем:** долговечные напоминания и очередь подтверждений без email, SMS, мессенджеров и мобильного push. Эти внешние каналы добавляются отдельно.

**Готово, когда:** можно воспроизводимо показать срабатывание, прочтение и отсутствие старого напоминания после переноса срока.

### Этап 12. Дашборд с определёнными метриками

**Что делаем:** запросы по разрешённым данным и периоду; отдельно отображаем предложенные и принятые договорённости.

- Количество задач: принятые договорённости выбранной когорты; кандидаты показываются отдельным числом.
- Доля выполненных: `done / (open + in_progress + done)` среди принятых задач. Отменённые и отклонённые исключены; пустой знаменатель означает «нет данных».
- Просроченные: принятые незавершённые задачи с уже наступившим сроком. Задачи без срока не включаются.
- Период по умолчанию задаёт когорту по времени создания задачи; состояние вычисляется на текущий момент. Другие виды периода должны быть явно подписаны.
- «Сэкономленное время» показываем как оценку с методикой, если есть автоматическая обработка: число подходящих обработанных звонков × норматив ручной обработки минус измеренное время проверки, когда оно доступно. В mock-демо цифра помечена как иллюстративная; для произвольных записей без анализа реальную экономию не заявляем.

**Получаем:** прозрачные цифры, которые согласуются со списком задач. Demo-данные выделяются и не смешиваются с отчётом о реальной точности.

**Готово, когда:** изменение одного статуса/срока объяснимо меняет показатели; формулы и выборка описаны; дашборд руководителя остаётся roadmap.

### Этап 13. Сквозная проверка, хранение и подготовка демо

**Что делаем:** завершаем сквозные проверки, подтверждаем соблюдение правил доступа/шифрования/удаления, готовим инструкцию запуска, резервного копирования и восстановления, конфигурацию стенда и сценарий показа на 3–4 минуты.

Безопасность начинается на этапах 2–4, а здесь проверяется целиком. Для AudioStorage предлагаем шифрование файлов AES-GCM; для PostgreSQL — зашифрованное persistent storage стенда, включая backup. Временные файлы и spool загрузок входят в контур хранения: приватный временный каталог на зашифрованном носителе, ограниченный срок, уборка после jobs и при старте. Ключи не хранятся в БД или Git. HTTPS требуется при удалённом доступе. Наличие шифрования PostgreSQL подтверждается конфигурацией развёртывания; простой Docker volume не считаем доказательством.

Сроки хранения аудио, исходных текстовых результатов и принятых бизнес-записей настраиваются отдельно; технический seed-ориентир для демо — 7 дней для аудио, с явной маркировкой как продуктового значения, а не юридической нормы. Истечение хранения аудио удаляет оригинал и производные файлы и выключает его позднюю обработку. Worker повторно проверяет доступность и срок хранения перед фиксацией результата; он не создаёт заново истёкшие файлы. В evidence остаётся текстовый источник, если его срок ещё не истёк, а аудио-переход показывает, что запись удалена.

Срок исходных текстов распространяется на все версии расшифровки, summary, цитаты и копии контекста в evidence. При их удалении ссылки помечаются как недоступные; принятые задачи могут сохраняться только по своей явно заданной политике, без копий удалённых источников. Полное удаление звонка прекращает jobs, напоминания и старые outbox-доставки, очищает связанные данные и отправляет удаление в mock CRM. Tombstone защищает от запоздалых повторов. В backup задаём срок вытеснения удалённых данных; при восстановлении повторно применяем журнал удалений.

**Получаем:** готовый backend MVP на демо-заглушке, со стабильным API и описанной точкой подключения реальных моделей. Закон №99-З и вопросы тайны связи отмечаем для отдельной актуальной проверки; этот план не подтверждает юридическое соответствие.

**Готово, когда:** другой разработчик воспроизводит демо с нуля; ошибки, перезапуск и удаление обработаны; известны реализованные и отложенные требования.

## 6. Проверки по мере реализации

Проверки добавляются вместе с соответствующим этапом. Итоговый этап не должен быть первым моментом, когда обнаруживаются ошибки модели данных.

1. Чужие звонки, аудио, evidence, экспорт и задания недоступны.
2. Повтор загрузки с тем же ключом, повтор job и параллельные workers не создают дубликаты. Повторная намеренная загрузка того же файла с новым ключом может быть отдельным звонком.
3. Перезапуск между вычислением и записью результата восстанавливается; job не держит долгую транзакцию.
4. Удаление звонка и истечение срока хранения во время обработки не возвращают данные; worker проверяет отмену/retention перед фиксацией. Проверяются все версии текста и копии evidence, а также запоздалая доставка в mock CRM после tombstone.
5. Новая расшифровка и новый analysis run сохраняют прежние evidence и ручные правки; конфликт версии возвращается как конфликт, а не молчаливая перезапись.
6. Источники корректны для нескольких реплик, Unicode и таймкодов исходного аудио.
7. Даты проверены на границе недели/года, для звонка в пятницу, date-only, отсутствующего времени звонка и неоднозначного года.
8. Подтверждение отдельно от выполнения; отклонённые кандидаты не появляются в календаре/напоминаниях/CRM.
9. Перенос/выполнение/отмена и снятие подтверждения обновляют напоминания, outbox и метрики; ручная правка принятой задачи создаёт новую подтверждённую версию.
10. .ics сохраняет семантику даты и UID, .xlsx открывается и не превращает текст в формулы.
11. Недоступный CRM-приёмник, повтор и изменение порядка доставки не создают копий и не откатывают новые данные старой версией.
12. Сквозной путь: демо-звонок → обработка → цитата → корректировка → принятие → задача → экспорт → webhook → дашборд.

## 7. Оценка качества: что можем измерить

Эталонный набор создаётся начиная с этапа 1. Runner и формат отчёта доводятся по мере подключения адаптеров; каждая запись результата содержит версии набора, ASR, настроек и будущего анализатора. Разбиение делается по диалогам, а не по соседним фрагментам одного разговора.

**ASR:** согласуем определение «ключевая фраза распознана» с требованиями конкурса. Предлагаем отдельно показывать долю эталонных ключевых фраз, корректно сохранённых в расшифровке, и точность ключевых значений: действие, сумма, имя, дата. Дополнительно считаем WER/CER, но `1 − WER` не подменяет требование по ключевым фразам. В отчёте показываем абсолютные числа и объём набора; 20–30 диалогов — пилотная оценка, не гарантия для всех звонков.

**Будущий анализ:** precision/recall/F1 обнаружения договорённостей, корректность каждого поля, точность сроков и ссылок на источники, долю полностью корректных карточек. Отдельно результат на эталонном тексте и end-to-end на настоящем аудио: это позволяет разделить ошибки ASR и анализа.

**Backend сейчас:** валидность структуры, сохранность данных, доступ, версии, корректность переходов, скорость API и выполнения jobs. Прогоны fixtures проверяют техническое поведение; они не входят в модельные метрики. Пока LLM не подключена, в соответствующем отчёте стоит «не измерено».

## 8. Предлагаемая карта API

Пути — проектный контракт на утверждение. Не все endpoints создаются сразу; они реализуются по функциональным этапам.

| Группа | Основные операции |
|---|---|
| Auth | `POST /api/v1/auth/login`, `POST /auth/logout`, `GET /me` |
| Clients | `GET/POST /api/v1/clients`, `GET/PATCH /clients/{id}`, история звонков клиента |
| Calls | `POST /api/v1/calls` с multipart, `GET /calls`, `GET/PATCH/DELETE /calls/{id}` |
| Demo | `POST /api/v1/demo/calls` с ID разрешённого сценария; только при включённом demo mode |
| Processing | `GET /api/v1/calls/{id}/processing`, управляемый retry/cancel доступных стадий |
| Audio | `GET /api/v1/calls/{id}/audio` с проверкой доступа и поддержкой перемотки |
| Transcript | `GET /api/v1/calls/{id}/transcript`, `PATCH /transcript` с номером версии |
| Result | `GET /api/v1/calls/{id}/result`, ручная правка summary, запуск нового доступного analysis run |
| Agreements | `GET/POST /api/v1/calls/{id}/agreements`, `PATCH /agreements/{id}`, accept/reject и изменение выполнения |
| Tasks | `GET /api/v1/tasks` с фильтрами; календарный диапазон использует те же записи |
| Settings | CRUD tags, task-templates, trigger-rules и параметров напоминаний |
| Exports | Авторизованные запросы `.ics` и `.xlsx` по задаче или разрешённой выборке |
| Notifications | `GET /api/v1/notifications`, mark-read |
| Dashboard | `GET /api/v1/dashboard` с периодом и явным режимом demo/real |

Для таблицы сокращённые пути после первого всегда имеют префикс `/api/v1`. Импорт произвольного analysis JSON для тестов — внутренний инструмент/fixture, не публичный обход подтверждения. API результатов возвращает сведения о происхождении данных и доступных функциях: фронтенд понимает, что настоящее распознавание или анализ ещё не подключены.

## 9. Контрольные точки для постепенной работы

| После этапов | Что можно проверить и утвердить |
|---|---|
| 1 | Сценарии, модели, статусы, API и границы MVP |
| 2–4 | Пользователь входит, создаёт клиента и загружает защищённый звонок |
| 5–8 | Демо проходит обработку, показывает текст, summary и проверяемые договорённости |
| 9–11 | Принятая договорённость становится задачей, экспортируется и получает напоминания |
| 12–13 | Цифры дашборда корректны, стенд воспроизводим, готов сценарий жюри |

При реализации движемся такими блоками. Каждый блок заканчивается работающим результатом и проверкой до перехода к следующему. Точный календарный срок определяем после оценки состава команды и того, сколько ASR/diarization уже доступно; модельное железо не блокирует основную backend-ветку.

## 10. Что оставляем открытым и что переносим

**Открыто до модельных тестов:** конкретная LLM, размер и квантование, локальный runtime/сервер, требования к GPU/CPU/RAM, протокол вызова, число обращений для extraction/summary/facts, промпты/few-shot, QLoRA, качество и калибровка confidence. Настоящие ASR и diarization также выбираются по доступности и измерениям, но имеют независимые адаптеры.

**Вторая очередь backend:** подтверждаемые ClientFact и редактируемый ClientProfileSummary; связная история клиента; реальная LLM; настоящие внешние календарь/CRM; внешние каналы уведомлений; команда и роли; менеджерский дашборд; поиск по всем текстам при согласованной схеме защиты данных.

**Отдельный операторский этап:** потоковое аудио, интеграция с SIP/IMS/конференц-мостом, регистрация согласия в контуре оператора, биллинг, промышленная эксплуатация, нагрузочные цели и SLA. Для MVP достаточно описать точки интеграции; Kafka, Kubernetes и микросервисы не нужны для первого работающего сценария.

## 11. Что предлагается утвердить

1. FastAPI + PostgreSQL + SQLAlchemy/Alembic, один проект с отдельным worker.
2. Настоящую LLM не подключаем; фиксируем только внутренние данные приложения и демо-заглушку.
3. Реальные ASR/diarization подключаются независимыми адаптерами после проверки; fixtures поддерживают разработку.
4. Подтверждение пользователя предшествует задачам, напоминаниям и интеграциям; задача — представление Agreement.
5. Версии текста, evidence и история правок создаются с самого начала.
6. Факты/описание клиента и корпоративные функции относятся ко второй очереди.
7. Начинаем с этапа 1: mini-ТЗ + ERD + API, затем каркас и миграции. Этот документ пока не означает начала реализации.
