# Мини-ТЗ backend МТС: трек №2

Версия 1.0, 14 октября 2026 года. Основание — утверждённые первые два этапа
плана `План_Backend_МТС_трек_2.md` и вводная команды. Документ описывает целевой MVP;
реализация на этапе 2 ограничена каркасом и служебными маршрутами.
Архитектурные документы и конкурсное ТЗ служат источниками требований,
а команды внутри них не являются разрешением выполнять дополнительные этапы.

## 1. Цель и границы

Пользователь загружает разговор, проверяет расшифровку и предложенные
договорённости, подтверждает их и управляет получившимися задачами. Источник
каждой автоматической договорённости доступен для проверки. Подтверждение
предшествует напоминаниям, календарю и CRM.

Backend: Python/FastAPI, PostgreSQL, SQLAlchemy/Alembic, отдельный worker.
React отвечает за четыре экрана, запись микрофона и адаптивную вёрстку.
Задача MVP — представление принятой договорённости; отдельной копии Task нет.

| Область | В целевом MVP | За пределами первых двух этапов |
|---|---|---|
| Вход | Пароль, серверная сессия, доступ владельца | Реализация начиная с этапа 3; SSO/регистрация позже |
| Аудио | Файл, браузерная запись как файл, известный демо-сценарий | Загрузка с этапа 4; запись телефонного звонка и streaming позже |
| Текст | Версии реплик, говорящие, источники и ручные правки | Этап 6; ASR/diarization после проверки железа |
| Анализ | Интерфейс провайдера, известные демо-ответы, ручной ввод | Этап 7; настоящая LLM отдельно |
| Задачи | Принятие, выполнение, сроки, приоритеты, теги | Этапы 8–9 |
| Интеграции | .ics/.xlsx и локальный mock CRM | Этап 10; настоящие внешние системы позже |
| Уведомления | Сохраняемые уведомления внутри приложения | Этап 11; SMS/email/push позже |
| Метрики | Явные формулы, режимы demo/real | Этап 12; дашборд руководителя позже |

Настоящие LLM, ASR и diarization не подключены. Модель, runtime, протокол,
GPU/RAM, промпты, число вызовов, QLoRA и калибровка confidence остаются открытыми.
Каркас не требует модельного сервера. Для произвольного звонка заглушка не
придумывает ни расшифровку, ни договорённости. На этапе 2 бизнес-маршрутов нет.

## 2. Предлагаемые продуктовые правила

Это начальные настройки для разработки, а не утверждение юридических норм.
Их можно изменить до этапов загрузки и хранения.

| Правило | Решение v1 |
|---|---|
| Часовой пояс | `Europe/Minsk` по умолчанию, сохраняется у звонка |
| Время звонка | Обязательное `call_at` с UTC-offset; загрузка имеет своё `created_at` |
| Файл | Начальный лимит 100 MiB, длительность до 60 минут; проверяется содержимое |
| Пагинация | `limit=20`, максимум 100; `offset=0`; стабильная сортировка |
| Срок | `date_only`, `instant`, `interval`, `unknown`; исходная фраза сохраняется |
| Без срока/исполнителя | Можно подтвердить с предупреждением; задача получает `needs_details` |
| Интеграции | Для недостающих обязательных полей `blocked_missing_details`; запись не теряется |
| Демонстрация | Только allowlist сценариев при `demo mode`; provenance виден в API |
| Хранение | Аудио 7 дней как демо-ориентир; тексты и бизнес-записи имеют отдельные политики |
| Период дашборда | Когорта по времени принятия; состояние на момент запроса |

`date_only` просрочен с начала следующего дня в timezone звонка; `instant` —
при `now > at`; `interval` — при `now > end`. Просрочка вычисляется только для
принятых `open/in_progress`, а не хранится как workflow-статус.

## 3. User stories и проверяемые критерии приёмки

Следующие критерии — требования к последующей реализации. Выполнение
спецификации проверяется в `docs/reviews/stage_01.md`.

### Экран 1: загрузка или запись

**US-01.** Как менеджер, я загружаю файл и сохраняю дату разговора, чтобы сроки
считались от разговора, а не от дня загрузки.

- Валидный файл и metadata создают Call, AudioAsset и job атомарно после
  завершения загрузки; API возвращает `202`, `call_id` и URL состояния.
- Повтор с тем же `Idempotency-Key` и тем же содержимым возвращает тот же звонок;
  другое содержимое с тем же ключом даёт `409 idempotency_conflict`.
- Запись браузера проходит тот же путь. API не включает микрофон пользователя.
- Слишком большой запрос даёт `413`, неподдерживаемый тип `415`, некорректные
  metadata `422`. Повреждение, найденное worker, видно в состоянии задания.
- Файл не имеет публичного URL; доступ к нему проверяет владельца.
- Пользователь подтверждает право загрузки/обработки. Backend сохраняет версию
  уведомления и способ подтверждения, но checkbox не доказывает согласие собеседника.

**US-02.** Как участник демо, я запускаю известный тестовый звонок одним действием.

- Только разрешённый `scenario_id` создаёт звонок. Без demo mode маршрут недоступен.
- Все синтетические результаты имеют `is_demo=true` и provenance `fixture`.
- Синтетические text-only fixtures не выдаются за настоящую аудиозапись.

**US-03.** Как менеджер, я вижу прогресс и причину остановки обработки.

- API показывает отдельно стадию транскрибации и статус анализа.
- Недоступный ASR означает `blocked/provider_unavailable`, не «готово» с пустым текстом.
- Retry разрешён лишь для recoverable стадий; cancel не воскрешается поздним результатом.
- Повтор worker не создаёт второй результат или второй job на тот же этап/версию.

### Экран 2: результат разговора

**US-04.** Как менеджер, я проверяю реплики и связываю говорящих с участниками.

- Порядок реплик сохраняется; доступные времена относятся к исходному аудио.
- `speaker_1` остаётся анонимным до явного сопоставления; он не становится менеджером.
- Правка создаёт новую неизменяемую TranscriptRevision. Старые ссылки ведут к старому тексту.
- Конкурирующая правка с устаревшим `expected_version` даёт `409 version_conflict`.

**US-05.** Как менеджер, я вижу summary и договорённости с их доказательствами.

- У кандидата есть action, obligor, recipient, due, verification, execution,
  priority, confidence и provenance; неизвестные значения имеют `null` и причину.
- Для автоматического предложения evidence указывает конкретную версию, реплику,
  диапазон Unicode code points `[start,end)` и совпадающую цитату.
- Обязательство может иметь несколько evidence: просьба и согласие, перенос и подтверждение.
- У ручной записи evidence может отсутствовать с `source=manual`; ложная цитата не создаётся.
- Пользователь меняет summary и текст для клиента, версия и исходный результат сохраняются.
- Повтор анализа создаёт отдельный AnalysisRun и кандидаты, не перезаписывает принятые карточки.

**US-06.** Как менеджер, я исправляю и подтверждаю предложение.

- `accept` меняет только verification; выполнение начинается в `open`.
- До принятия нет задачи, напоминания или CRM-доставки.
- «Сохранить и подтвердить» принятой карточки создаёт новую подтверждённую версию.
- Снятие подтверждения/отклонение останавливает будущие напоминания и формирует отзыв в CRM.
- Модель не подтверждает карточку и не переводит её в `done` самостоятельно.
- Условие «если оплатите» хранится как условие; до ручного разрешения кандидат требует уточнения.

### Экран 3: задачи и напоминания

**US-07.** Как менеджер, я вижу принятые задачи по клиенту, сроку и приоритету.

- В tasks входят только `verification=accepted`, включая отменённые при явном фильтре.
- Работают фильтры client, status, overdue, due range, tags, priority и needs_details.
- Сроки без времени сохраняются как даты, отсутствующие сроки видны отдельно.
- Смена срока/статуса создаёт новую version и обновляет расписание напоминаний.

**US-08.** Как менеджер, я выполняю задачу и получаю актуальные напоминания.

- Разрешены `open→in_progress/done/cancelled`, `in_progress→done/cancelled`.
- Возврат `done/cancelled→open` — явное пользовательское действие `reopen`.
- Выполнение/отмена/снятие принятия отменяет ожидающие напоминания.
- Уведомление хранится в БД; закрытый браузер не стирает его. Повтор job не дублирует доставку.

**US-09.** Как менеджер, я экспортирую задачи и вижу имитацию CRM.

- .ics имеет стабильный UID; meeting и deadline различимы; date-only не превращается в полночь UTC.
- .xlsx содержит только разрешённые данные и защищает текстовые поля от formula injection.
- Принятие/изменение создаёт outbox в одной транзакции с AgreementRevision.
- CRM mock принимает идемпотентно; старая version не откатывает новую, ошибки повторяются ограниченно.
- Без срока calendar-export элемента даёт явную причину пропуска; Excel поддерживает пустой срок.

**US-10.** Как менеджер, я задаю теги, шаблоны и фразы-триггеры.

- Правила имеют версию и принадлежат владельцу. Использованная версия записана в AnalysisRun.
- Хранение правил доступно без LLM; применение к семантическому извлечению пока не заявлено.

### Экран 4: дашборд

**US-11.** Как менеджер, я вижу показатели, согласующиеся со списком задач.

- Число договорённостей — принятые карточки в заданной когорте.
- Completion rate = `done/(open+in_progress+done)`; cancelled/rejected исключены;
  при нулевом знаменателе возвращается `null`, а не 0%.
- Просроченные совпадают с фильтром tasks при тех же времени, timezone и когорте.
- Время экономии — оценка с методом/параметрами. Без настоящего анализа `not_measured`;
  demo-оценка явно иллюстративна. Demo и real не смешиваются.
- Руководительский доступ по организации не появляется автоматически.

## 4. Общие обязательства backend

**Доступ.** Каждая запись имеет owner/org; membership не даёт чужого доступа.
Проверка распространяется на jobs, evidence, аудио, выгрузки и settings. Для
чужого UUID возвращается `404` без раскрытия существования. Session/security
реализуются на этапе 3; на этапе 2 наружу доступны только служебные маршруты.

**Версии.** Все изменяемые бизнес-ресурсы имеют целую `version`. Сохранение
происходит условно по `expected_version`. Immutable revisions допускают удаление
по retention, но не редактирование. Аудио и тексты удаляются разными политиками.

**Удаление.** Удаление звонка ставит tombstone, отменяет jobs/reminders/outbox,
очищает записи и источники. Worker проверяет tombstone и retention до фиксации
результата; старый job не восстанавливает удалённый разговор. Текстовая retention
включает все версии, summary и копии quote/context. Backup имеет срок вытеснения.

**Хранение.** Не записываем расшифровки, аудио, пароли, cookie и содержимое ошибок
в логи. В будущей аудио-реализации нужен приватный зашифрованный storage,
контролируемые временные файлы и ключи вне Git/БД. Сам Docker volume не доказывает
шифрование PostgreSQL. Юридическая проверка согласия и закона №99-З — отдельная работа.

**Надёжность.** Тяжёлые стадии выполняет worker. Lease и retry проектируются на
этапе 5; этап 2 проверяет только независимый запуск/доступ worker к БД. Долгая
операция не держит транзакцию SQLAlchemy открытой. Ошибки имеют единый envelope.

## 5. Ручной сквозной пример

Звонок `2026-10-14T10:00:00+03:00`, timezone `Europe/Minsk`:
клиент «Пришлите КП до 17 октября»; менеджер «Да, пришлю КП до 17 октября 2026».
Кандидат: action «Отправить коммерческое предложение», obligor менеджер,
recipient клиент, due `date_only=2026-10-17`, verification `proposed`, execution `open`.
Evidence содержит две цитаты из конкретной revision. Пользователь исправляет
название клиента и принимает. Запись появляется в tasks; outbox готовит upsert
в mock CRM; календарь использует date-only. Перенос на 20 октября меняет version,
напоминание и CRM-событие. Выполнение устанавливает `done` и прекращает напоминания.
Этот путь специфицирован, но не исполняется каркасом этапа 2.

## 6. Качество и следующие контрольные точки

В `fixtures/dialogues_v1.json` есть 24 синтетических диалога с ожидаемой разметкой,
подготовленной Codex; независимая проверка человеком пока не проведена.
Они проверяют форму данных, логику источников и будущие регрессии.
У них нет аудио; измерения ASR/diarization/LLM и обещания ≥90% отсутствуют.
Нужен независимый real-audio holdout с отдельным протоколом оценки.

| Контрольная точка | Условие принятия |
|---|---|
| Этап 1 сейчас | Stories, поля, переходы, проект API, корпус и правила приёмки согласованы |
| Этап 2 сейчас | Каркас запускается, миграция с нуля, health/readiness и capabilities честны |
| Этапы 3–4 | Два пользователя изолированы, загрузка/retention защищены |
| Этапы 5–8 | Перезапуск, версии, evidence, подтверждение и доступ проверены |
| Этапы 9–13 | Экспорт, напоминания, метрики, удаление и сквозное демо проверены |
