# Пилотный эталонный набор и границы оценки

Версия 1.0, 14 октября 2026 года. Файлы:
`fixtures/dialogues_v1.json` и `fixtures/dialogue.schema.json` (JSON Schema
Draft 2020-12). Набор и ожидаемые ответы подготовлены Codex как синтетические
примеры для разработки. Независимая проверка разметки человеком ещё не проведена.

## 1. Что готово

Созданы **24 синтетических текстовых диалога** с заранее заданной ожидаемой разметкой:
20 актуальных кандидатов в 19 диалогах; 5 диалогов без действующего обязательства,
включая одну явную отмену. События переноса, исправления и отмены сохранены отдельно.
Два участника на большинстве примеров; отдельные примеры имеют неизвестного
говорящего или третье лицо. Нет телефонных номеров, реальных персональных данных
и записей людей. Имена и ситуации вымышлены.

У набора и каждого диалога выставлены:

```json
{
  "synthetic":true,
  "text_only":true,
  "no_real_audio":true,
  "usage":"development_fixture"
}
```

В верхнем уровне `split=development_only`, а `measurement_status` ASR,
diarization и LLM — `not_measured`. Пример, известный fixture-провайдеру,
не входит в независимое испытание этого провайдера.

Этот набор позволяет обсуждать предметную логику, загружать известные demo
fixtures на будущих этапах и проверять структуру/даты/ссылки на источники.
**Он не измеряет распознавание речи, разделение говорящих, качество LLM или ≥90%.**
На этапе 2 HTTP-загрузка этих fixtures и модельный evaluation runner отсутствуют.

## 2. Формат

| Поле | Значение |
|---|---|
| schema_version / dataset_version | Формат `1.0`, набор `synthetic-text-v1` |
| annotation_source | `codex_authored_fixture` |
| human_review_status | `pending`; человеку предстоит подтвердить ожидаемые ответы |
| offset_unit | `unicode_code_points` |
| offset_convention | `zero_based_half_open` |
| dialogues[].id | Уникальное `syn_01`..`syn_24` |
| call_at / timezone | Явная дата звонка с +03:00, `Europe/Minsk`; не today |
| transcript_revision | `r1`, локальная immutable fixture revision |
| participants | Локальные id, имя либо null, role, identity_state |
| segments | Порядок, speaker/participant mapping, текст, null start_ms/end_ms |
| gold.agreements | Текущее обязательство на конец разговора, не автоматическая Task |
| gold.events | Изменения `cancelled/rescheduled/corrected` и evidence |
| gold.key_phrases | Эталонные spans для будущего определения ключевых фраз |
| gold.negative_reason | Причина отсутствия итоговых обязательств; null у положительных |

`gold.agreements[]`:

- `id` — уникален внутри диалога; `action` — нормализованное действие;
- `obligor_participant_id` / `recipient_participant_id` — ссылки на локальных участников;
- `due` — union из domain_model: date_only/instant/interval/unknown, original_text,
  basis_call_at, timezone, причины неопределённости;
- `condition` — условие либо null, `needs_details` — чего не хватает;
- `eligibility=candidate` — предложение можно показать пользователю для проверки;
  `needs_review` — условие/участник требуют отдельного уточнения;
- `evidence` — непустой массив точных source spans.

Eligibility — метка эталона, **не** состояние verification. Fixtures не помечены
accepted и не создают напоминания или CRM. Неизвестный due сохраняется объектом,
причина deadline_not_stated не превращается в выдуманную дату. `ambiguous=true`
в этом наборе обозначает любой неразрешённый срок, включая отсутствие фразы.
После уточнения пользователем normalizer будет хранить это отдельной revision.

Evidence указывает `transcript_revision`, `segment_id`, `start_cp/end_cp`, `quote`.
Offsets — 0-based, `[start,end)`, считаются по Unicode code points самого текста
реплики. Quote точно равен соответствующему slice. Это не байты и не UTF-16.
Пробелы, «ё», кавычки и emoji считаются в исходном виде; после разметки текст не
нормализуется. `syn_23` намеренно имеет внутренний span с emoji.
Аудио-таймкоды null: присваивание вымышленных миллисекунд запрещено.

JSON Schema проверяет структуру/enum/форматы, но не целостность ссылок, совпадение
цитат, хронологию и уникальность локальных id — дополнительно нужны semantic checks.
В Python slice строки естественно считает Unicode code points; frontend JavaScript
должен применять code-point массив (`Array.from(text)`) при такой адресации.

Не все естественные диалоги имеют единственную бесспорную разметку. Эти fixtures
фиксируют выбранные правила v1. При изменении политики создаём dataset v2 и
описываем отличие, чтобы старые метрики не сравнивались с новой разметкой молча.

## 4. Приёмка набора сейчас

1. Количество 20–30 (фактически 24), все id уникальны.
2. Synthetic/text_only/no_real_audio истинны; measurement_status везде not_measured.
3. Date/time имеют offset и timezone, basis_call_at равен дате разговора.
4. Segment.position непрерывен; все participant/speaker/evidence references существуют.
5. Для каждого span `0≤start_cp<end_cp≤len(text)` и slice равен quote.
6. Все start_ms/end_ms null; нет случайно выдуманного аудио.
7. Negative cases не дают актуальных candidates; отмена сохранена событием.
8. Relative normalization проверяется от call_at, включая границу года.
9. Unknown/условие/неизвестный участник не подменяются автоматически заполненной карточкой.
10. JSON синтаксически корректен; schema отдельно валидируется Draft 2020-12 validator
    с FormatChecker. Проверка формы не называется модельной оценкой.

Пример проверки при установленном `jsonschema` (дополнительный инструмент,
не runtime dependency API):

```python
import json
from pathlib import Path
from jsonschema import Draft202012Validator, FormatChecker

data = json.loads(Path("fixtures/dialogues_v1.json").read_text(encoding="utf-8"))
schema = json.loads(Path("fixtures/dialogue.schema.json").read_text(encoding="utf-8"))
Draft202012Validator.check_schema(schema)
Draft202012Validator(schema, format_checker=FormatChecker()).validate(data)
for dialogue in data["dialogues"]:
    segments = {s["id"]: s for s in dialogue["segments"]}
    for item in dialogue["gold"]["agreements"] + dialogue["gold"]["events"]:
        for ev in item["evidence"]:
            text = segments[ev["segment_id"]]["text"]
            assert text[ev["start_cp"]:ev["end_cp"]] == ev["quote"]
```

## 5. Что понадобится для настоящей оценки

До заявления о точности соберём отдельный набор настоящих аудиозаписей или
отдельно озвученных диалогов с разрешением на обработку. Запись synthetic script
впоследствии всё ещё синтетическая; её нельзя незаметно назвать реальным клиентским
разговором. В наборе фиксируем шум, каналы, длину, speakers, язык, способы записи.

Нужны эталонная ручная транскрипция, реальные таймкоды ключевых фраз,
обязательства/evidence/даты, независимая разметка двумя участниками команды и
разрешение разногласий. `development`, `validation` и закрытый `holdout` разделяем
по целым разговорам, спикерам/источникам по возможности. Нельзя иметь соседние
фрагменты одного звонка в train/dev и holdout.

Результат сохраняет dataset version, split, run id, provider/runtime версии,
settings/prompt version, дату запуска, абсолютные числитель/знаменатель и ошибки.
Порог ≥90% из конкурсного ТЗ относится к распознаванию ключевых фраз; сначала
согласуем критерий «правильно распознана» и единицу подсчёта. WER/CER показываем
дополнительно: `1-WER` не подменяет этот показатель.

Для будущего анализа измеряем отдельно precision/recall/F1 обнаружения,
корректность action/participants/due/evidence и долю полностью корректных карточек.
Два прогона — на эталонном тексте и end-to-end на аудио — отделяют ошибки ASR от
анализа. Confidence провайдера не считается accuracy. До подключения настоящих
адаптеров в отчёте стоит «не измерено», а не 0% или 100% по fixture-ответам.
