# Этап 2 — каркас проекта и воспроизводимый запуск

Дата: 14 октября 2026 года. Область: запуск backend и технические проверки;
предметный backend начинается с этапа 3.

## Что сделано и зачем

- Создан Python-пакет `mts_backend` в `backend/src`. Отдельные процессы API и
  worker позволят добавлять длительную обработку без её выполнения в HTTP-запросе.
- FastAPI публикует liveness, readiness и capabilities. Readiness зависит от БД и
  baseline-миграции, а не только от возможности открыть HTTP-порт.
- Настройки берутся из окружения и валидируются. URL подключения — `SecretStr`;
  список CORS содержит точные origins. Production запрещает включённые API docs.
- SQLAlchemy 2 использует async-движок с psycopg. Alembic поддерживает online и
  offline-режим; baseline `0001_bootstrap` создаёт только учёт версии миграций.
  Таблицы клиентов, звонков, задач и пользователей ещё не созданы.
- Добавлены Dockerfile, Compose и Makefile. Compose проверяет PostgreSQL перед
  миграцией; API и worker стартуют после успешной миграции. Python runtime работает
  от непривилегированного пользователя, порты опубликованы только на loopback.
- Зависимости зафиксированы в lock-файлах с хешами. `.env.example` содержит только
  явно обозначенные демо-значения; `.env` исключён из Git.
- [README](../../README.md) содержит запуск, настройки, ограничения и диагностику.
- Для заполненного диска Docker добавлен отдельный host-storage режим:
  `compose.host-storage.yaml`, `make up-host/down-host/logs-host/migrate-host`.
  PostgreSQL хранит данные в `.local/postgres`; обычный named volume сохранён.
- Снимок OpenAPI трёх реализованных маршрутов сохранён в
  `docs/api/openapi-stage2.json`.

Worker этого этапа не обрабатывает звонки: он проверяет инфраструктуру и работает
в цикле с корректным завершением. Настоящие ASR, diarization и LLM отключены;
демо-обработка известных fixtures также пока не запускается.

## Ревью результата

Каркас соответствует границам первых двух этапов. Выбор модели и доступность GPU
не влияют на запуск. Empty baseline намеренно не превращает проектную ERD в
непроверенную бизнес-схему: реализация отношений, владельцев и авторизации идёт
следующим этапом. `capabilities` отделяет работающие технические функции от
запланированного продукта.

Порядок запуска защищает от старта приложения с отсутствующей миграцией;
readiness дополнительно проверяет состояние во время работы. Отдельный worker
готов как процесс, но lease, захват jobs, повторы и обработка отмены относятся к
этапу 5. Mock CRM не нужен до этапа 10.

Структурированные логи не копируют тела запросов, SQL, URL подключения или модельные
результаты; Uvicorn запускается с `--no-access-log`. Сам каркас не заменяет
авторизацию, шифрование хранилища или процедуры удаления. PostgreSQL volume
сохраняет данные между обычными перезапусками, однако наличие volume не доказывает
шифрование на диске.

## Критерии приёмки

| № | Проверка | Ожидаемый результат |
|---|---|---|
| 1 | `cp .env.example .env`, `docker compose config --quiet` | Конфигурация валидна; секреты не печатаются |
| 2 | `make up`, `docker compose ps -a` | `db` healthy, `migrate` завершён с exit 0, `api` healthy, `worker` работает |
| 3 | `curl --fail http://127.0.0.1:8000/health/live` | HTTP 200 и JSON liveness |
| 4 | `curl --fail http://127.0.0.1:8000/health/ready` | HTTP 200 после применения baseline |
| 5 | `curl --fail http://127.0.0.1:8000/api/v1/capabilities` | Модели и бизнес-функции не заявлены доступными |
| 6 | Открыть `/docs` и `/openapi.json` | Видны только реализованные технические endpoints |
| 7 | `make migrate` дважды | Оба прогона успешны; нет дополнительных таблиц или повторных изменений |
| 8 | SQL-запрос к `alembic_version` | Одна версия `0001_bootstrap` |
| 9 | `docker compose stop db`, затем GET `/health/live` и `/health/ready` | Live = 200; ready = 503 без DSN/traceback в HTTP-ответе |
| 10 | `docker compose start db`, дождаться ready | Ready возвращается к HTTP 200; worker продолжает работу |
| 11 | `make down`, затем `make up` | Volume сохранён, миграция повторно безопасна, API возвращается в ready |
| 12 | `make setup PYTHON=python3.12`, `make check` | Python-пакет устанавливается, pytest и Ruff успешны |
| 13 | Проверить порт и пользователя контейнера | Worker не публикует порт; backend UID = 10001; host ports = loopback |
| 14 | Остановить worker | SIGTERM завершает процесс без бесконечного ожидания очередного poll |
| 15 | Некорректный URL/CORS и production с docs=true | Настройки отвергнуты до запуска приложения; секрет не попадает в ошибку API |

Дополнительная ручная проверка baseline с демо-учётной записью:

```sh
docker compose exec db psql -U mts_dev -d mts_dev -Atc 'SELECT version_num FROM alembic_version'
docker compose exec api id -u
docker compose logs --tail=100 api worker migrate
```

Ожидаемый вывод первых двух команд: `0001_bootstrap` и `10001`. Проверяющий просматривает
логи на отсутствие credentials и пользовательского текста. Установка пакета и
lint/tests не требуют GPU; Docker acceptance требует работающего Docker daemon.

Обычный named volume на этом компьютере не смог инициализировать PostgreSQL:
`initdb` получил `No space left on device` при создании `pg_wal` внутри диска
Docker. Поэтому полный запуск и сохранение данных проверены в host-storage
режиме. Это ограничение локального Docker-хранилища; критерий обычного named-volume
запуска остаётся непроверенным в данном окружении. Настройки и чужие Docker-данные
не изменялись. Для текущего компьютера рабочая команда — `make up-host`.

Независимое ревью подтвердило согласованность конфигурации и порядка миграций.
По результатам исправлены/уточнены: явная зависимость `sqlalchemy[asyncio]` для
greenlet на ARM, поддерживаемый Starlette тестовый клиент `httpx2`, заголовок Allow
для 405 и защита проверки тестового URL без пароля. Критических замечаний к
каркасу по итоговому ревью не осталось.

Команда обычного `make test` без test URL пропускает 5 PostgreSQL integration
проверок. Как подготовить выделенную БД и повторить полный прогон, описано в README.
Все проверки относятся к техническому каркасу; точность моделей не измерялась.

Healthcheck PostgreSQL теперь выполняет `SELECT 1` в настроенной прикладной БД
после `pg_isready`. Проверено: существующая БД даёт exit 0, заведомо отсутствующая
БД — ненулевой exit; одна лишь доступность сервера не объявляет его готовым.
После изменения API и БД healthy, миграция завершена с exit 0, worker работает;
live, ready, capabilities и OpenAPI возвращают HTTP 200.
